# 朱紫：一次配对、同一会话连续派送

## 调研结论

官方 `kwsch/SysBot.NET` 的 master 固定提交 `844c1f31face95bc8e1cfec9c9b7cbd9f7a62895` **没有同会话批次开关**。

- [官方 SV 交换器](https://github.com/kwsch/SysBot.NET/blob/844c1f31face95bc8e1cfec9c9b7cbd9f7a62895/SysBot.Pokemon/SV/BotTrade/PokeTradeBotSV.cs)：每只完成后无条件 `ExitTradeToPortal`。
- `LastTradeDistributionFixed` 只省去重复输入密码；`StartFromOverworld=false` 只是从 Portal 开始，都不代表保留伙伴会话。
- `AllowBatchCommands` 是 PKHeX Batch Editor 属性编辑许可，与批量交换无关。
- `zyro670/NotForkBot.NET` 默认分支 `NotKoiTest` 提交 `5ea0d371b18d27120bcad6f1d3c4680687fe5281` 的 SV 也每只退出；此结论不概括其所有衍生分支。

已有真正的同会话实现：[Secludedly/FusionBot](https://github.com/Secludedly/FusionBot/blob/31594ca8bf60afdb6a8ddfa32064569398df334e/SysBot.Pokemon/SV/BotTrade/PokeTradeBotSV.cs#L913-L1308)，固定提交 `31594ca8bf60afdb6a8ddfa32064569398df334e`，AGPL-3.0。

其核心是**一个批次容器、只在首只配对、后续留在盒子中逐只替换 B1S1**。不是同时向多个盒子槽预填宝可梦。后续没有 B 键导航；依赖交换后等待及同一工作格的下一次注入。

本项目借鉴并在代码中注明上述会话循环来源，保留现有 AGPL-3.0；没有整体搬入其线上连接、AutoOT、整批自动重试或 Discord 状态管理。

## 当前实现

- 一次网页提交生成一个批次；**所有成员先在电脑中完成生成和校验**，全部通过才排队。
- 只有根任务进入真正的 SysBot FIFO，根任务持有按原顺序排列的成员。单只仍用原路径；2–12 只走本地 USB 同会话路径。
- 第一只输入密码、搜索并校验伙伴；中间成员不退出、不重新搜索、不读写在线 NID；最后一只完成才退出。
- 每只分别更新 `准备中/交换中/已完成`，同批后续显示 `同批等待`；显示第 i/N 只。
- 未开始时可**整批取消**；任一成员入口都只移除同一个根任务。开始后不拆批取消，以免后台仍持有已撤销成员。
- 会话失败就停止本轮，不换一个伙伴继续发。已完成项保留，当前项结果不确定时失败，未开始项标为 `本批已中断 · 未派送`。失败批次从不整体重排。
- USB 失败仍锁存并取消运行；下一批保留队列但不会自动连接，必须核对收货后手动重连。程序重启不保留内存队列。

## 接收端怎么操作

1. 一次粘贴整批，点击「一起派送」。分两次提交就是两个批次，不会跨订单无限续连。
2. 用 **03180318** 搜索一次。
3. 收完一只，**不要退出交易盒子**。按网页提示先选择下一只交换材料，等派送端显示正确的下一只后再确认。
4. 看到「本批 N 只全部完成」才退出。另一个新批次需重新配对。
5. 初次验证只用皮卡丘＋伊布两只以及不会交换进化的普通材料，确认成功后再扩大批次。

## 为什么没有“同时写满多个盒子格子”

这是一个独立功能，并非同会话交换的必要条件。官方 `ReadBoxPokemon` 明确只支持 B1S1，槽位不连续，不能使用 `BoxStartOffset + slot * 0x158` 猜地址。

另一个维护中的 LiveHeX 分支提供 SV4.0.0 连续盒子数据区：

- [LPPointer.cs](https://github.com/santacrab2/PKHeX-Plugins/blob/90410f2681a0a72680d12280a1e0f14715e67dff/PKHeX.Core.Injection/Protocols/LPPointer.cs#L255-L333)
- 其链为 `[[[[main+47350d8]+1C0]+30]+9D0]`，不是官方交易对象的 `D8→8→B8→30→9D0→0` 链。
- 没有证据证明两个区域在交易中的同步关系，所以**本版不加入未经实机验证的多格预写**，也不宣称实现了同时摆满多格。

仍仅使用盒子 1 第 1 格。该格会逐只覆盖，不得放收藏。每只实际收到的材料会先保存到程序数据目录的 `received/<订单ID>.pk9`，再允许下一只覆盖工作格；这是电脑文件档案，不是自动搬到另一个游戏槽。保存失败则停止后续，已完成交易仍如实显示，避免下一次覆盖而丢失材料数据。

## 同会话安全边界

- 下一只注入前确认仍离线、在交易盒子、伙伴姓名/TID/SID匹配，并刷新和检查对方个体指针。
- 依赖已读到的合法接收结果、EC/详情与预先提供的材料匹配，不能只看工作格变化就冒充成功。
- 保留首次检测交换后至少25秒、额外5秒等待以及工作格稳定读取。**0x14状态也覆盖动画，稳定数据和定时不等于已掌握精确的动画结束信号。** 这是仍需实机验证的边界，不伪称完全解决。
- 后续要求新的材料变化，严格重复个体/相同EC与头部的材料可能保守拒绝；超时不偷偷使用旧材料确认。
- 批次中强制拒绝双方会交换进化的组合，避免进化/学招菜单延长造成错误注入。
- 不添加未经证实的 B 键步骤，不在错误后盲目导航或自动重放整批。

## 验证范围

单只和“每只重新配对”的老流程已有真实设备成功记录；**不能用它们证明本版同会话多只已经实机成功**。

本次运行全解决方案测试、批次生命周期与Fake设备异常测试、实际生成与HTTP/浏览器下单取消测试。浏览器测试强制 `SYSBOT_WEB_NO_HARDWARE=1`，不会占用已连接的真实NS，也不会在验收时派送。

需要实机验收：两只普通个体保持同一连接完成；第二只材料变化；对方中途退出；动画时机；不同USB断线时点。首次请保留日志，按“已完成/未派送/结果未确认”逐项核对，不整批盲目重发。
